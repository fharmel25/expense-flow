## 2. Phases

Each phase ends with a **checkpoint** you can verify yourself. The time estimates are rough.

### Phase 1 – Domain + unit tests (≈1 h)
- **Files:** `Domain/Common` (DomainException, InvalidStatusTransitionException, UtcGuard), `Domain/Enums`, `Domain/Entities` (User, Expense, ExpenseHistory, PushToken).
- **Rules inside the Domain:**
  - amount > 0, at most 2 decimals, and fits decimal(12,2);
  - a receipt is required;
  - the expense date can't be in the future;
  - status flow Submitted → InReview → Approved/Rejected only;
  - a rejection needs a reason;
  - no self-approval;
  - the workflow is attached once;
  - `User.IsManagerOf` (a manager decides only for their own team);
  - UTC-only dates.
- **Tests:** `tests/ExpenseFlow.UnitTests/Domain/*`, one test (or more) per rule.
- **Checkpoint:** `dotnet test` passes, and `/verify` shows these rules as covered.

### Phase 2 – Application layer (≈1 h)
- **Interfaces** (implemented later in Infrastructure): `IAppDbContext`, `ICurrentUser`, `IClock`, `IPasswordHasher`, `ITokenService`, `IReceiptStorage` (create a write-only or read-only SAS URL), `IWorkflowService` (start/resume), `INotificationClient`.
- **Use cases** (one MediatR handler each): Login, GetMe, CreateReceiptUploadUrl, SubmitExpense, GetMyExpenses, GetExpenseById, GetPendingForManager, ApproveExpense, RejectExpense, RegisterPushToken, MonthlyReport.
- **FluentValidation** validators for every request. They reject bad input with **400** before it reaches the Domain.
- **Application exceptions:** NotFoundException (404), ForbiddenException (403).
- **Ownership checks live here:** you can only see your own expenses, unless you're that employee's manager (`IsManagerOf`).
- **Tests:** handler tests with fake interfaces. They cover:
  - another team's manager gets Forbidden;
  - an employee can't read someone else's expense;
  - **approve and reject both trigger a notification**;
  - submit starts exactly one workflow.
- **Checkpoint:** `dotnet test` passes.

### Phase 3 – Infrastructure (≈1.5 h)
- **EF Core + Npgsql:**
  - an `AppDbContext` with one configuration class per entity;
  - `decimal(12,2)`, enums stored as text, `timestamptz` for every DateTime, `date` for ExpenseDate;
  - a **unique index on PushToken.Token** (no duplicates).
- **Migrations:** an `InitialCreate` migration, plus a **seed** with 1 manager and 2 employees (development only).
- **Password hashing** (Identity PasswordHasher) and a **JWT token service** (signing key read from user-secrets).
- **Blob receipt storage:**
  - a SAS URL scoped to *one blob*, write-only, valid 5 minutes, for upload;
  - a read-only SAS valid 5 minutes, for viewing;
  - the blob name is generated by the server (`receipts/{userId}/{guid}.jpg`), never taken from the client;
  - the container is private. Locally it runs on **Azurite**, with CORS set on the storage account.
- **Checkpoint:** `dotnet ef database update` creates the tables, and pgAdmin/DBeaver shows them.

### Phase 4 – API layer (≈1.5 h)
- **Controllers:** Auth, Receipts, Expenses, Devices, Reports. Delete the WeatherForecast sample.
- **Global exception handler (ProblemDetails):**

  | Error | HTTP status |
  |---|---|
  | Validation | 400 |
  | Not authenticated | 401 |
  | Forbidden | 403 |
  | NotFound | 404 |
  | InvalidStatusTransition / unique-constraint violation | 409 |
  | DomainException | 422 |
  | Anything else | 500, with no internal details |

- **Security and setup:**
  - JWT bearer auth, with every endpoint `[Authorize]` except login;
  - the Manager role on the approval endpoints, plus the `IsManagerOf` check in the handler;
  - CORS (web app origin from configuration);
  - Swagger with a Bearer button;
  - HTTPS redirection only outside Development;
  - a `/health` endpoint.
- **Idempotent submit:** the app generates the expense ID. A retry with the same ID returns the existing expense instead of creating a duplicate.
- **Integration tests** (`WebApplicationFactory` + the real PostgreSQL in Docker):
  - 401 without a token;
  - 403 for the wrong manager;
  - 404 for an unknown ID;
  - 409 when approving twice;
  - 400 for a reject without a reason;
  - Elsa tables live in the `elsa` schema;
  - all DateTime columns are `timestamptz`.
- **Checkpoint (in Swagger/Postman):** login → upload URL → submit → list → approve. Bad requests return 4xx, never 500.

### Phase 5 – Elsa workflow (≈1.5 h)
- Elsa 3, persisted with EF Core in **PostgreSQL schema `elsa`**.
- **Workflow defined in C#:** Start(expenseId) → **StartReview** → **NotifyManager** → **Wait for decision** (bookmark) → branch Approved/Rejected → **NotifyEmployee** → End.
- **Custom activities call Application services**, so business rules stay out of the workflow wiring.
- **Submit** saves the expense, starts the workflow and stores `WorkflowInstanceId` (attached once).
- **Approve/Reject** applies the Domain method, then resumes the bookmark.
- **If a notification fails, it's logged and the status is still saved.** A failure is never recorded as "sent".
- **Tests:** submit → InReview; approve → Approved + 2 notifications; reject → Rejected + reason; a second approve → 409.
- **Checkpoint:** in Postman, run the full flow and see the completed instance in the `elsa` tables.

### Phase 6 – Node notification service (≈45 min)
- `notifications/`: TypeScript + Express + expo-server-sdk. Configuration comes from `.env`, loaded with Node's built-in `--env-file` option (no extra library), plus a committed `.env.example`.
- **`GET /health`.**
- **`POST /notify`:**
  - requires the `x-internal-key` header (otherwise 401);
  - validates the body (otherwise 400);
  - checks each token with `Expo.isExpoPushToken`;
  - sends in chunks;
  - returns per-token results, including **DeviceNotRegistered**.
- **The API removes dead tokens** based on that result.
- **Errors return a clean 4xx/5xx JSON body.** No unhandled promise rejections.
- **Tests:** 401 without the key, 400 on a bad body, invalid tokens reported, with Expo mocked **in tests only**.
- **Checkpoint:** `npm test` passes, and the `Invoke-RestMethod` health call works.

### Phase 7 – Expo app (≈3 h)
- **Create the project in `app/`:** `create-expo-app`, then set `slug: "expenseflow"` and `owner: "fharmels-team"`, then run `eas init --id 48edb5ed-…`, then `npm run reset-project` to remove the example screens.
- **Libraries, installed with `npx expo install` only:** expo-image-picker, expo-image-manipulator, expo-secure-store, expo-notifications, expo-device, expo-dev-client, @tanstack/react-query.
- **`.env`** (`EXPO_PUBLIC_API_URL`), with a committed `.env.example`.
- **Building blocks:**
  - **API client:** adds the JWT automatically, handles 401 → logout, and turns 4xx responses into readable messages;
  - **token storage helper:** SecureStore on mobile, browser storage on web;
  - **AuthContext.**
- **Screens:** Login → My Expenses (list, status badge, pull-to-refresh) → New Expense (photo, compress, upload with the SAS URL, submit with a client-generated ID) → Expense Detail (receipt, history) → Approvals (Manager only; reject needs a reason) → Profile/Logout.
- **Push registration:** after login, on mobile only. Tapping a notification opens the expense.
- **Checkpoint:** the full flow works on the Samsung (Expo Go) and on the web, and `npx expo lint` + `npx expo export --platform web` pass.

### Phase 8 – Push on Samsung (≈1 h, started early because the cloud build queues)
- Create the Firebase project and Android app (the package name matches `app.json`), and add `google-services.json`.
- Upload the FCM V1 service-account key to the Expo credentials. **Never commit that key.**
- Run `eas build --profile development --platform android` and install the build on the Samsung.
- **Checkpoint:** an employee submits, the manager gets a push, the manager approves on the web, and the employee gets a push.

### Phase 9 – iOS check (≈30 min)
- Add the `ios-simulator` profile in `eas.json`, then run `eas build --profile ios-simulator --platform ios`. **No Apple account is needed.**
- Upload the build to Appetize.io and walk through every screen, using a gallery image (that simulator has no camera and no push).
- **Checkpoint:** screenshots of Android, iOS and web.

### Phase 10 – Monthly report optimization (≈45 min)
- `GET /reports/monthly`: grouped in SQL, with AsNoTracking and DTO projection.
- Seed about 500k expenses (with `generate_series`), then run **EXPLAIN ANALYZE as a baseline**.
- Add indexes in a migration (**schema change, needs your OK**): (ExpenseDate, Status), (EmployeeId, ExpenseDate) with INCLUDE (Amount, Category), and a partial index on InReview.
- Run EXPLAIN ANALYZE again, and record the before/after numbers in `docs/PERFORMANCE.md`.
- **Checkpoint:** the timings show an Index Scan and a measured gain. That's your CV line.

### Phase 11 – Azure deployment (≈1.5 h, **costs money, needs your OK for each resource**)
- Resource group `rg-expenseflow`.
- **Resources:**
  - PostgreSQL Flexible Server (Burstable B1ms);
  - a Storage Account with a private `receipts` container and CORS;
  - an App Service Plan (Linux B1) with `expenseflow-api` and `expenseflow-notify`;
  - Static Web Apps (Free tier) for the web build;
  - Key Vault + Managed Identity;
  - Application Insights.
- **No secrets in settings.** App Service settings point to Key Vault (Key Vault references).
- **Checkpoint:** the end-to-end check passes against Azure, from the Samsung and the browser.

### Phase 12 – Azure DevOps CI/CD (≈1 h)
- The code lives on **GitHub**. In Azure DevOps, create a project and a **GitHub service connection**, then create each pipeline from its YAML file in the GitHub repo.
- `pipelines/api.yml`, `pipelines/notifications.yml` and `pipelines/web.yml`, each with path filters and Build → Deploy stages.
- **Pipeline contents:**
  - the **API** pipeline runs `dotnet test` and generates an idempotent migration script;
  - the **Node** pipeline runs `npm test`;
  - the **web** pipeline runs lint and the web export.
- **Secrets** live in a variable group linked to Key Vault. Optionally, an EAS build step uses an Expo token stored as a secret.
- **Checkpoint:** a push to `main` on GitHub builds and deploys automatically. You push and commit yourself.

### Phase 13 – Final verification and demo prep (≈30 min)
- `/verify`: every check PASSED, and every testable rule covered.
- `/review`: no Critical/High findings.
- The manual end-to-end check from CLAUDE.md, steps 1–5.
- `README.md` (architecture diagram, how to run, screenshots) and `docs/TALKING-POINTS.md` (interview answers).

## 5. Risks and fallbacks

| Risk | Fallback |
|---|---|
| Docker won't start | Install PostgreSQL natively (`winget install PostgreSQL.PostgreSQL.16`) |
| Elsa integration takes too long | Keep the same workflow steps, with a simpler bookmark; the essential parts are submit → wait → resume |
| EAS cloud build queue is slow | Start the Android development build early in Phase 7 |
| Phone can't reach the local API | PC IP + firewall rule, or `npx expo start --tunnel` |
| Short on time | Phases 1–8 + 10 give a complete demo. Phases 11–12 can be reduced to "API deployed + pipeline YAML" |
